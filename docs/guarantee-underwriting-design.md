# 保証引受（guarantee underwriting）設計 — N-20（2026-08-05）

## 一言で
「Vouch の ALLOW に金を賭ける」商品の引受判定を、公開中の /accuracy と
**同一の実測レポート**から決定論的に導く。実装は純関数
`src/lib/guarantee/underwriting.ts`（テスト: `tests/guarantee-underwriting.test.ts` 7件）。

## なぜ堀か
スコアAPIは模倣可能。しかし保証は「精度の実績」を担保にしないと成立せず、
実績は /accuracy の蓄積（=時間と顧客）でしか作れない。後発はこの順序を飛ばせない。

## 引受ルール（fail closed）
| 条件 | 閾値 | 落ちた場合 |
|---|---|---|
| 解決済み判定数 | ≥ 200（`UNDERWRITE_MIN_RESOLVED`） | 提供不可 |
| ALLOW損失率 | 計測済み かつ ≤ 2% | null/超過とも提供不可 |
| 補償上限 | min($5,000, 解決済み件数×$1) | — |
| 保険料率 | max(0.5%, 損失率×5) | — |

- 値付けの入力は `AccuracyReport` のみ。**公開数字より甘い内部数字で引き受けない**
- 欠格事由は全件列挙（blockers[]）。理由コードは機械可読

## 現状と発動条件
- **休眠**。事業判断は approval-queue **AQ-016**
- 発動 = 解決済み200件到達 → Legal審査（保証業該当性）→ 商品化
- それまで対外的に言及しない（実測なしの匂わせは brand 原則違反）

## コード側の受け皿（2026-08-06・N-21 で整備・**既定OFF**）

商用化判断が下りた日に「実装」ではなく「フラグ反転」だけで動くところまで配線済み。
純関数より先は一切進めない（実際の補償金支払い・保険数理・法務は Takeshi＋専門家判断）。

- **APIの口**: `GET /api/v1/guarantee/quote`（認証必須）。
  `isGuaranteeUnderwritingEnabled()`（env `GUARANTEE_UNDERWRITING_ENABLED=true` のときのみ真・
  本番の暗黙有効化なし）が false の間は**認証より前に 404**を返す＝機能が存在しないのと同じ。
  有効時は公開 /accuracy と**同一の** `fetchAccuracyRows`→`computeAccuracyReport`→`underwrite()` を通し、
  `UnderwritingQuote`（canOffer / maxCoverageUsd / premiumRate / blockers / basis）を返す。
  甘い内部数字での値付けは構造的に不可能。
- **UIの口**: 未実装（意図的）。上記APIが唯一の入口。ダッシュボード表示は商用化判断後に足す。
- 現時点の応答は解決済み200件未満で `canOffer:false` + `blockers:["insufficient_resolved_verdicts:…"]`。
  これが今の正直な答え。

## 料金・補償条件ドラフト（純関数の現行値・**確定ではない**）

`src/lib/guarantee/underwriting.ts` の定数がそのまま初期ドラフト。商用化時に見直す前提。

| 項目 | ドラフト値 | 根拠 |
|---|---|---|
| 対象 | ALLOW 判定のみ | WARN/BLOCK は保証しない（保証するのは「安全と言い切った判断」） |
| 引受下限 | 解決済み ≥ 200件 | /accuracy の MIN_SAMPLE=10 より遥かに厳しい。金を賭けるには10観測では足りない |
| 引受可否 | ALLOW損失率 計測済み かつ ≤ 2% | 未計測・超過とも fail closed |
| 補償上限/件 | `min($5,000, 解決済み件数×$1)` | 実績が増えるほど上限が上がる（薄い実績で大金を賭けない） |
| 保険料率 | `max(0.5%, 損失率×5)` | 実測損失率に安全係数5倍。損失率が上がれば料率も上がる |

**未確定（商用化時に決める）**: 保証の発動条件の厳密な定義（「外した」の判定手続き・証拠要件・
異議申立）、支払い通貨と決済経路、保証期間（判定後どれだけの窓）、1顧客あたり総エクスポージャー上限。

## 商用化前に必要な意思決定（Takeshi＋専門家・コード側では解けない）

1. **補償原資**: 支払い準備金をどこから積むか（自己資金／再保険／プール）。原資なしの保証は不履行リスク
2. **補償上限の妥当性**: 上式の `$5,000` 上限・`×$1/件` 傾きが事業リスク許容度に合うか（保険数理レビュー）
3. **法務レビュー（最重要）**: この商品が各法域で「保険業」「保証業」に該当するか。該当なら免許要件。
   利用規約・免責・準拠法。「情報提供のみ」の現行ディスクレーマと保証商品の整合
4. **保険料率の税・会計処理**: 受領保険料と支払補償の会計区分
5. **発動運用**: クレーム受付・調査・支払いの人手フロー（個人運営で回るか、上限件数の設計）
6. **撤退条件**: 損失率が閾値を超えたときの新規引受停止と既存保証の扱い

これらが揃うまで `GUARANTEE_UNDERWRITING_ENABLED` は false のまま。対外言及もしない。
